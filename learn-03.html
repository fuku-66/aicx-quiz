3-1. ナレッジマネジメントの基礎

覚えること

  • 情報 vs 知識: 情報=事実の記述 / 知識=判断の根拠
  • 暗黙知: 経験や勘に基づき、言葉や文書として整理されていない知識
  • 形式知: 言葉・数値・図表で表現され、文書として共有できる知識
  • AIエージェントが参照できるのは形式知だけ
  • ナレッジベース: 業務マニュアル・FAQ・対応履歴・規程を整理・保存したもの
  • ナレッジマネジメント: 個人に属する知識を整理・共有・活用できる状態にする取り組み

暗黙知が形式知化されない理由

  • 言語化の困難さ: 熟練の判断は本人も意識にのぼらない
  • 知識の囲い込み: 「自分しか知らない」が価値だと感じる心理的障壁

SECIモデル（野中郁次郎）

  • 共同化（Socialization）: 暗黙知→暗黙知（一緒に体験して移転）
  • 表出化（Externalization）: 暗黙知→形式知（言語化）
  • 連結化（Combination）: 形式知→新たな形式知（組み合わせ）
  • 内面化（Internalization）: 形式知→暗黙知（実践で身体化）

RAGとファインチューニングの使い分け

  • RAG: 回答の度に外部ナレッジを参照（料理本を引く）。更新頻度が高い情報に向く
  • ファインチューニング: モデル自体に追加学習（シェフに体で覚えさせる）。自社らしさ・文体・トーンに向く
  • 知識更新が頻繁な情報には一般にRAGが適している
  • 両者は組み合わせて使うことが多い

試験頻出ポイント

  • AIエージェントの精度競争は「モデルの性能競争」ではなく「知識の質の競争」に移行
  • ナレッジベースの品質がRAG精度を直接左右する

3-2. データの種類と特性

覚えること

  • 構造化データ: テーブル形式（DB・Excel）。検索・集計・比較が容易。従来ITが得意
  • 非構造化データ: メール・PDF・画像・音声・動画。企業データの**約80%**を占める。LLMが真価を発揮
  • 半構造化データ: JSON・XML・名刺など。完全構造ではないがタグやキーで部分的に整理
  • データ種類と処理の担い手:
    • 構造化 → API・定型処理
    • 非構造化 → LLM
    • 半構造化 → AIエージェントの入出力インターフェース

メタデータ

  • 「データについてのデータ」。文書本体ではなく属性情報（カテゴリ・対応OS・最終更新日など）
  • RAGの検索精度を左右する重要要素

試験頻出ポイント

  • 非構造化データの処理こそLLMの最大の強み
  • 同一業務フロー内でも、データ種類ごとに最適な担い手を割り当てる
  • 典型変換パターン: 非構造化→LLM→半構造化（JSON）→API→構造化

3-3. RAGの仕組み

覚えること

  • RAG（Retrieval-Augmented Generation）: 検索拡張生成。LLMが知らない情報を必要時に検索して与える仕組み
  • RAGはモデルパラメータを更新しない。検索結果をプロンプトに含めるだけ

2フェーズ

  • 保存フェーズ: ①チャンク分割 ②ベクトル化 ③インデックス化
  • 検索・生成フェーズ: 質問のベクトル化 → セマンティック検索 → 関連チャンクをLLMに渡し回答生成
  • セマンティック検索: キーワード一致でなく意味の近さで検索
  • グラウンディング: 外部文書・データに基づいて回答させる方法

チャンク設計

  • 大きすぎる → 複数トピックが混在し検索ノイズ
  • 小さすぎる → 文脈が失われ回答質低下
  • 目安「1トピック1チャンク」

RAG精度を左右する2段階

  • 検索の精度: 関連チャンクが適切に取得できているか
  • 生成の精度: チャンク内容に忠実かつ過不足ない回答ができているか
  • 精度低下時は両者を切り分けて原因特定

試験頻出ポイント

  • 「検索と生成のどちらに原因があるか」を切り分けて改善
  • メタデータの設計が検索精度を大きく左右
  • まず動くものを作り、フィードバックで段階的に精度を高める

3-4. AIガバナンスと法務

覚えること

  • AIガバナンス: AIエージェントの利用・管理・監督に関する体制・ルール・プロセスの総称
  • AIポリシー: 「入力許可データ」と「入力禁止データ」を文書化
  • AIポリシーに万社共通の正解は存在しない（業種・データ機密レベル・サービス形態で異なる）
  • 利用ガイドライン: ポリシーを日常業務の判断に落とし込んだもの。具体性が肝心

法的リスク3領域

  • 著作権リスク: 学習データ・生成物の権利問題
  • 個人情報保護法リスク: マスキングや本人同意・安全管理措置が必要
  • 責任分界点リスク: AIには法的責任を負わせられない。設計者・承認者・経営者の責任を明文化

ストラテジストの橋渡し役

  • 技術用語 → 法務向け翻訳が必要
  • 例: 「RAGで検索」→「社内文書テキストが外部AIサービスに送信される。個人情報・営業秘密が含まれる場合は対応が必要」

試験頻出ポイント

  • 責任構造はHuman-in-the-Loopで「人間が確認・承認」する設計に落とす
  • ガバナンスはリスクを止めるためではなく、許容範囲で安全に活用する土台

3-5. AIエージェントが読みやすいデータを作る

覚えること

  • 人間に読みやすい≠AIに読みやすい（セル結合は人にはOK、AIには崩壊）
  • 原則: 「AIエージェントが見えないものは存在しないのと同じ」

7つの習慣

  1. 固有名詞で書く（「例の件」NG）
  2. 「見た目」より「構造」で作る（セル結合NG・1セル1データ）
  3. 正しい入力がラクにできる環境（プルダウン・マスタ参照）
  4. 重要画像に注釈（スクショにキャプション）
  5. 日付とカテゴリタグを入れる（メタデータ）
  6. バージョン管理は履歴機能で（ファイル名管理NG）
  7. AIがアクセスできる場所に置く（SharePoint等）

AI Readyデータ（Gartner）

  • 正確性: データに矛盾がない
  • 可視性: 所在・意味・メタデータ整備
  • 追跡可能性: 出所と変更履歴
  • 安全性: アクセス制御・プライバシー保護
  • Gartner予測: 2026年までにAI Readyデータの不備でAIプロジェクトの60%が中止される

既存データの整形範囲

  • 「全部きれいにしてからAI導入」では永遠に始まらない
  • 利用対象範囲から優先的に整形
  • 過去データ遡及より、今後の記録を新テンプレで蓄積

ナレッジベース鮮度管理（4ステップ）

  • 変更検知 → 変更箇所の反映 → 古い情報の除外 → 品質確認

試験頻出ポイント

  • ハーネスエンジニアリング: AIモデルの賢さでなく「動ける環境設計」で品質が決まる
  • AIメタデータ自動付与は人間レビューと組み合わせる（Human-in-the-Loop）

3-6. AIプロジェクトの進め方

覚えること

  • AIプロジェクト特有の3つの不確実性: 技術面 / 業務適合性 / 効果面
  • 通常のIT開発は「何を作るか」が決まっており「どう実装するか」が不確実だが、AIでは「そもそも解けるか」が不確実

全体フロー: A実験フェーズ（PoC） → B本運用フェーズ

  • 判断ゲートで制御
  • AフェーズはPoC失敗・繰り返しが前提（撤退判断も価値ある成果）

Aフェーズ5ステップ

  1. 初期相談: 「やりたいこと」→「解くべき課題」変換
  2. 業務分析・現場視察: AIプロジェクト最重要工程。観察モード（提案しない）
  3. 提案・スコープ設計: 一点集中。MVPで最小限から
  4. モデル開発・MVP開発: 作り込みすぎない。「検証できる状態」を作る
  5. 効果検証: 定量・定性両方で判定 → Go / 修正 / 撤退

試験頻出ポイント

  • ベースライン測定はPoC開始前または同時に行う鉄則
  • アジャイル・デザイン思考はAI固有の不確実性に対処しきれない

3-7. AIプロジェクトの成功の定義：3層フレームワーク

覚えること

  • 3層フレームワーク:
    • 第1層 効果層: ビジネスに効果が出ているか（最初に定義）
    • 第2層 定着層: 現場の人が使っているか（効果から逆算）
    • 第3層 精度層: AIが正しく答えられるか（定着から逆算）

重要な二重構造

  • 定義の順序: トップダウン（効果→定着→精度）
  • 達成の順序: ボトムアップ（精度→定着→効果）

ベースライン測定

  • 効果層の最大のミスはベースライン未測定
  • PoC開始前に現状値を記録

定着層の測定

  • PoC中は定性的代理指標（短期データでは利用率の解釈が困難）
  • 本運用後は定量指標
  • 「使いたくない」理由の4分類: 精度不信 / UX問題 / 業務フロー不適合 / 心理的抵抗

精度層

  • 目標値は逆算で決める（現在の人間水準、現場受容水準、業務上許容リスク）
  • 業務によって重視指標が異なる: 品質検査=見逃し少（再現率）、スパムフィルタ=誤検知少（適合率）

試験頻出ポイント

  • 「正答率80%達成＝成功」と判断する罠
  • 「使いたくない」原因を誤診すると精度ばかり追って解決しない
