4-1. 自動化レベルの進化論と実務における最適解

覚えること

  • 「いきなり全自動」は多くのプロジェクトを失敗に導く
  • 段階的アプローチが組織の信頼を積む

4段階の自動化レベル

  • Lv.1 アドホック: 必要なときに都度使う（ChatGPTそのまま利用）。仕組み化されていない
  • Lv.2 カスタムチャットボット: GPTs・Gem・Claudeプロジェクト等で専門性を持たせる。受動的な対話型
  • Lv.3 ワークフロー: トリガー起動で複数ステップを自動連鎖。「決められたレールを走る電車」。Dify・Zapier・Make・Copilot Studio
  • Lv.4 自律型エージェント: 目標から計画・実行を自ら組み立てる。「自家用車」。Manus・Claude Cowork等

レベル境界線

  • Lv.1とLv.2: 仕組み化されているか
  • Lv.2とLv.3: AIが自ら動くか + システム連携があるか
  • Lv.3とLv.4: フロー構造自体をAIが作ったか

試験頻出ポイント

  • MVPアプローチ: 最小限で価値を証明し、データに基づいて次の投資判断
  • Manusの教訓: ファインチューニングよりコンテキストエンジニアリング

4-2. ワークフロー設計 トリガーとアクション

覚えること

  • ワークフロー＝トリガー（きっかけ）+ アクション（処理）

トリガー3分類

  • 指示型:
    • チャット・音声指示
    • 手動実行（ボタン）
  • 定時型:
    • スケジュール実行（毎朝9時等）
    • 期限・日付ベース（契約更新30日前等）
  • 条件型:
    • イベントトリガー（CRMステータス変更等）
    • フォーム送信
    • Webhook（外部システムから通知）
    • 閾値トリガー（在庫数下回り等）

イベントトリガー vs Webhookの違い

  • イベントトリガー: ワークフロー側が監視
  • Webhook: 外部システム側が通知

アクション3分類

  • データ処理: APIコール（取得）・データ抽出/構造化・データ変換/整形
  • 生成・判断: コンテンツ生成・分類/振り分け・判断/条件分岐
  • 実行・連携: APIコール（送信）・ファイル操作・Human-in-the-Loop

試験頻出ポイント

  • データ取得と送信は方向が逆のAPIコール
  • HTAで分解した業務がそのままワークフロー設計図になる

4-3. ワークフロー設計 変数と条件分岐

覚えること

  • 変数: ワークフロー内でデータを一時保持する「名前付きの箱」
  • 変数のデータ源: トリガー情報 / 外部システム / 前アクション出力

条件分岐3種類

  • If/Else: 二択分岐（1,000万円以上 vs 未満）
  • ルーティング: 3方向以上への振り分け（業界別テンプレ4種）
  • フィルタリング: 通過/遮断の選別（受注成功のみ通過）

見分けのポイント

  • 2択 → If/Else
  • 3方向以上の振り分け → ルーティング
  • 通過/遮断の選別 → フィルタリング

エラーハンドリング

  • 「正常か？」のIf/Else応用
  • フォールバック: APIコール失敗時に「Slack通知して手動依頼」
  • 完全自動化でなく、人間が介入できる経路を残すのが責任ある設計

試験頻出ポイント

  • 条件分岐は「提案の成否に最も影響する変数」に絞る（細かすぎはメンテ困難・粗すぎは品質低下）
  • エラーハンドリングはHuman-in-the-Loop設計と直結

4-4. コンテキストエンジニアリング概論

覚えること

  • コンテキストエンジニアリング: LLMに渡す文脈情報を体系的に設計・管理する技術
  • Andrej Karpathy氏: 「LLMはOS、コンテキストウィンドウはRAM」
  • プロンプトエンジニアリングは指示文に焦点。コンテキストエンジニアリングはその上位概念（指示+文書+ツール+履歴すべて）

コンテキストエンジニアリングが解決する4課題

  • 入力可能な情報量の限界: コンテキストウィンドウ上限
  • 認識の限界（Lost in the Middle）: LLMは先頭・末尾を参照しやすく中間を見落とす
  • コンテキスト汚染: ハルシネーション混入による連鎖
  • コンテキスト混乱: 無関係/矛盾情報で推論阻害

LLMに渡す情報の7種類

  1. システムプロンプト: 役割・前提・制約・行動指針
  2. ユーザープロンプト: 都度の指示・入力
  3. 短期メモリ: 現セッション内の対話履歴
  4. 長期メモリ: セッションをまたぐ蓄積（手続き記憶/エピソード記憶/意味記憶）
  5. 外部知識（RAG）: 実行時にナレッジベース検索
  6. ツールの情報: 利用可能ツールの定義・使い方
  7. 構造化出力: JSONや特定テンプレ等の応答形式指定

4つの手法

  • Write（書き出し）: 重要情報を外部保存（ManusのToDoリスト）
  • Select（選択）: 必要な情報だけ取り出す
  • Compress（圧縮）: 要約・削減（情報欠落リスクあり最後の手段）
  • Isolate（分割）: 複雑問題を小さく分けて処理（マルチエージェント等）

4つの設計原則

  • 必要十分の原則: 「あれば便利」でなく「なければ正しい出力ができないか」
  • 構造化の原則: 重要制約は冒頭、参照と指示を区別、リスト・見出しで構造化
  • 鮮度の原則: 重要情報はコンテキスト後半に配置
  • 反復検証の原則: 1度で完成しない・フィードバックループで改善

ハーネスエンジニアリング

  • AIエージェントが「正しく動ける環境全体」の設計
  • 4領域: コンテキスト設計 / データ品質管理 / 出力の自動チェック / Human-in-the-Loop設計

試験頻出ポイント

  • 出力品質の問題はモデル変更前に「渡している情報」を疑う
  • 切り分け順序: 情報の欠落 → ノイズ → フォーマット → 最後にモデル変更
  • 「情報は多く与えるほど良い」は誤解。何を渡さないかの設計も重要
