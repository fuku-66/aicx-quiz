Ch.06 AIエージェントを実装する5Dモデル

公式テキスト Chapter 06 より要約 セクション数: 5

6-1. Step1 Discovery（発見・選定）

覚えること

  • 5Dモデル: Discovery → Definition → Design → Development & PoC → Deployment & Scale
  • Discoveryは「何を自動化するか」を決めるステップ。設計・プロトタイプはまだ作らない

ボトルネックの特定

  • プロセス全体の生産性を制約している最も弱い箇所
  • 特徴: 処理に時間がかかる / ミス頻発 / 属人化 / 反復的で付加価値が低い
  • Discoveryでは「どこに問題があるか」発見に集中。詳細分解はDefinitionで

AI適合性診断の3基準

  1. 非構造化データの処理を含むか: メール文面・報告書・画像はLLMの強み
  2. 文脈に応じた判断が必要か: 手順が完全に定義できる業務はRPAで十分
  3. ミスが許容できるか / HITLで補完できるか: 100%精度必須業務はAI不向き

AI適合性が低い業務

  • 100%正確性が法的要求される業務
  • 対人関係・共感が本質の業務
  • 極秘データで外部API送信不可
  • 物理的操作が伴う業務

優先順位マトリクス

  • 縦軸「効果の大きさ」× 横軸「実現のしやすさ」
  • 効果大かつ実現容易 → 最優先（クイックウィン）
  • 効果大で実現困難 → 中長期検討

試験頻出ポイント

  • 「ボトルネックだからAI化」でなく「ボトルネック かつ AI適合性が高い」業務を選ぶ2段階フィルタリング
  • クイックウィン選定基準: 短期成果 + 定量化可能 + 低リスク

6-2. Step2 Definition（定義・構造化）

覚えること

  • Definitionは「何を実現したいか」を具体化するステップ
  • 4つの成果物: 業務フローチャート / 要件定義書 / ペルソナ定義 / 合格基準

業務フローチャートによる暗黙知の可視化

  • 対象業務をフローチャートとして詳細可視化
  • HTAやIPOモデルの手法が本格的に活用される
  • 暗黙知のままだとAIと人間の役割切り分けが曖昧になり、Designで手戻り発生

要件定義書の4構成要素

  • 機能要件: 何をさせたいか（「スキル抽出」「適合度算出」）
  • 非機能要件: どの品質で動作してほしいか（30秒以内、24時間稼働）
  • 制約条件: 守るべきルール（性別・年齢を評価に用いない）
  • 前提条件: あらかじめ満たされているとみなす条件（PDFまたはWord提出）

ペルソナ定義

  • AI固有のペルソナでは「年齢・役職」より「AIエージェントの出力をどう使い、どんな判断を下すか」を描写
  • 直接ユーザーだけでなく間接ユーザー（出力を確認・監督する社内担当者）も定義
  • SIPOC分析の「出力受取者を漏れなく洗い出す」がここで活きる

合格基準の事前定義

  • PoCの合否判定に使う定量基準
  • 「なんとなく90%」でなく業務上の要求から逆算した根拠
  • 合格基準とKPIの違い: 合格基準=PoC合否の一回限り / KPI=運用中の継続成果測定

試験頻出ポイント

  • 「6ステップに分解しAIと人間の役割を決めた」はDefinitionの活動（Discoveryではない）
  • ストラテジストは完璧な要件定義書を一人で作る必要はなく「叩き台」を作る役割

6-3. Step3 Design（設計・プロンプト）

覚えること

  • Designは「何をやりたいか」を「どう実現するか」に落とし込むステップ
  • 3つの設計領域: コンテキスト設計 / I/O設計 / セキュリティ設計

コンテキスト設計

  • システムプロンプト: 役割・前提・制約を最上位指示として記述
  • Few-shotプロンプト: 入力例と出力例を組み合わせて期待する出力傾向を示す
    • 弱点: 偏った例だけだと判断が不安定。明確合格/不合格/境界事例をバランスよく
    • 補強策: 例からルールを抽出してプロンプトに組み込む
  • Chain-of-Thought: 思考過程を段階的に出力させる手法
    • LLMが一気に答えるより段階を踏む方が複雑問題で正確性が高まる
    • 推論モデルはこの考え方を行いやすく設計されている
    • トークン消費が増える点に注意

I/O設計

  • AIエージェントの出力は自然言語のままでは後続処理で困る
  • JSON形式で構造化（overall_score: 85, recommendation: 通過 のように明確化）
  • スキーマ: JSON構造をあらかじめ定めた設計ルール（項目・型・必須/任意・値範囲）
  • バリデーション: スキーマに沿っているか自動確認。違反時は再生成または人間引き継ぎ

セキュリティ設計

  • 「何を見せるか」と「何を出させるか」両方を管理
  • アクセス制御（入口側）: AIが参照できる情報範囲を制限。マスキング・特定文書遮断
  • ガードレール（出口側）: 出力内容に制限。不適切表現の検知・遮断・再生成

ストラテジストのDesign役割

  • 技術的実装はアーキテクト
  • ストラテジストは要件が設計に正しく反映されているか確認（橋渡し役）

試験頻出ポイント

  • 入力データのマスキングはセキュリティ設計（コンテキスト設計やI/O設計ではない）
  • 要件定義書記載はDefinition、JSONスキーマ設計はDesign

6-4. Step4 Development & PoC（開発・検証）

覚えること

  • 4概念の区別: プロトタイピング / サンドボックス / Human-in-the-Loop / フィードバックループ

プロトタイプ vs PoC vs MVP

  • プロトタイプ: 設計が技術的に動くかの試作品。利用者は開発・設計メンバー
  • PoC: 実現可能性検証。対象は意思決定者
  • MVP: 最小限の価値を実際の利用者に提供する実用品

サンドボックス

  • 本番環境から切り離された検証用環境
  • テスト用データを使い隔離環境で動作確認
  • パイロットとの違い: パイロットは実データ・実ユーザー・本番環境で行う限定運用

Human-in-the-Loop（Development段階での適用）

  • AI処理の中に人間の確認・判断・修正の工程を組み込む
  • 支援型では常時HITL、協働型では条件付きHITL

フィードバックループ

  • 「実行→評価→改善→再実行」の改善サイクル
  • Definitionの合格基準が「いつ終了してよいか」の判断基準として機能

Go / No-Go / Pivot判断

  • Go: 合格基準クリア → Deploymentへ
  • No-Go: 改善しても基準に届かない → 一旦中止
  • Pivot: 精度OKだがコスト想定超過等 → 方向修正（対象限定・モデル変更）

試験頻出ポイント

  • テストデータ・隔離環境＝Development、実データ・実ユーザー＝Deployment
  • 合格基準未達時はまずフィードバックループを回す（即時中止・基準引き下げNG）

6-5. Step5 Deployment & Scale（展開・定着）

覚えること

  • 検証済みAIエージェントを本番環境へ展開し、組織に定着させる最終ステップ

パイロット導入

  • 全社一斉でなく限定部門・チーム・業務で本番稼働
  • サンドボックスとの最大の違い: 実データと実ユーザーを対象に本番環境で運用
  • 重要な3理由: 実環境でしか見つからない問題 / 運用の仕組みも検証 / 小さな成功実績が次の展開根拠

ロールアウト

  • パイロット成功を受けて対象範囲を段階的拡大
  • 「同じ機能をより多くの人に届ける」
  • 機能自体は変わらない

スケーリング

  • 処理能力や適用範囲を拡大
  • ロールアウトと違い、対象業務拡大や新機能追加など能力拡張を含む

AI-SECIモデル

  • 従来SECIモデル（人間同士の知識変換）をAIエージェント文脈に拡張
  • 共同化: 担当者がAIの出力を日々確認、感覚的判断を蓄積
  • 表出化: 蓄積暗黙知をAIへのフィードバックとして明文化
  • 連結化: フィードバックをプロンプト/ナレッジに統合・横展開
  • 内面化: 改善されたAI出力を通じて新人が判断力を獲得

KPIモニタリング

  • 処理件数はアウトプット指標 → 差し戻し増加で工数膨らむリスクあり
  • 追うべきはアウトカム指標: 処理時間短縮率 / 判定一致率 / 入社後パフォーマンス
  • 採用スクリーニングAIでは「高スコア候補者が入社後活躍しているか」が本質指標（半年〜1年スパン）
  • 短期と長期のアウトカム指標を分けて設計

試験頻出ポイント

  • ロールアウト（同じ機能を多くの人に）とスケーリング（能力そのものの拡張）を区別
  • AI-SECIは「AIエージェントがサイクルの中核に入っている」点でSECIと区別
